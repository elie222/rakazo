# 需求规格（requirement-spec）

把一张需求票变成可开发、可验收的规格。产出**只能**贴到票评论，结构固定如下。

## 输出结构（缺一不可）

1. **目标与背景**：一句话解决什么问题；为什么现在做、影响谁。
2. **范围**：做什么；**明确不做什么**（至少一条，不许写「无」）。
3. **验收标准（DoD）**：可勾选、可执行的条目，每条有判定方法（跑什么/看什么/测什么）。
4. **约束**：仓库/环境/边界/不允许做的事。
5. **需要的输入**：凭证、账号、数据等（**只列名称**，不写任何密钥值）。

## 规则

- DoD 每项必须可由机器或人复核（例：「`pnpm test:compose-smoke` 绿」，不是「功能正常」）。
- 范围只写票内的事；溢出的想法写进「不做则说明」引导另立票。
- 引用现有仓库约定（README、CONTRIBUTING、checklist），不重复发明。
- 规格不完整时不硬凑：在票上提**具体问题**清单求澄清。

## 反模式（禁止）

- 用「用户体验更好」「性能优化」这类不可判定的词当 DoD。
- 把实现方案写死成唯一路径（spec 约束行为，不约束内部设计）。
- 在评论里泄露任何密钥/内部地址。
