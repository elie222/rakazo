# Reusable credentials

Ask a bot to connect an API using a key or password. It calls `request_secret` with a reference name and an HTTPS service origin. The protected card shows that origin before you save. Web, Electron and mobile use the same backend; the value is cleared from the input when submission starts and is omitted from messages, events and model input.

For example, the bot can request:

```json
{
  "label": "API key",
  "purpose": "api_key",
  "credential": {
    "name": "example_api",
    "origin": "https://api.example.test",
    "auth": { "type": "bearer" }
  }
}
```

The value is encrypted in Postgres `vault_credentials` using the deployment's `ENCRYPTION_KEY` (AES-256-GCM with record-bound authentication). Only the run's user can submit a reusable credential. It belongs to that user and survives later runs. By default it sits in the user's account vault, which every Space uses; a Space where the user keeps its own credentials has a separate vault that starts empty, so they have to be saved there again, and no other Space can read it. It is deleted when its owner is deleted, and a Space's own vault is also deleted with its Space. Names, destinations and authentication configuration are metadata; `list_secrets` returns those fields without values. No hosted credential service or prebuilt connector is required.

The bot uses `secret_request` to ask the backend to decrypt and inject the credential:

```json
{
  "name": "example_api",
  "url": "https://api.example.test/v1/items",
  "method": "GET"
}
```

Authentication supports Bearer tokens, a named header (`{"type":"header","name":"X-Api-Key"}`), and Basic authentication (`{"type":"basic","username":"api-user"}`). Basic uses the protected value as the password. Requests can send JSON, form-encoded or plain text bodies. The saved origin must match exactly, including port. Redirects and unsafe network destinations are rejected through the shared remote-request policy. Requests follow the existing action approval rules, have a 30-second deadline and a 1 MB response limit, and return at most 20,000 characters of redacted response content without response headers.

Self-hosted deployments can set `RAKAZO_SECRETS_ALLOW_PRIVATE_HTTP=1` to also allow plain `http://` origins on private or loopback addresses (for example `http://nas.local:8123` or `http://localhost:3000`). It is off by default. Credentials sent this way are unencrypted: anything on that network, or any local service on that port, can read them. Enable it only on a network you trust. Link-local and cloud metadata addresses stay blocked, and public origins still require HTTPS.

Calling `request_secret` again with the same name and configuration returns the saved reference. Add `"replace": true` to show another protected card and replace its value. `forget_secret` with `{"name":"example_api"}` removes the stored value and prevents future use; an already-started request may finish. Remove a credential before changing its origin or authentication configuration. Each user can save up to 100 credentials per bot, with values limited to 16,384 characters.

The model has no tool for reading these values, and the backend removes direct and common encoded echoes from API responses. The approved service still receives the credential: redaction cannot defend against a malicious service deliberately transforming it. Choose a service you trust and use appropriately scoped credentials.

This boundary supports authenticated HTTP requests. Injecting a site credential into an AI-controlled shell command, file or arbitrary environment variable would let those commands read it, so those paths are not exposed. A value you deliberately want in the bot's own shell is a command variable, below. APIs needing request signing, OAuth refresh, multiple credentials or custom protocols should use a connector adapter. Existing `request_secret` calls with a `connectionId` retain their one-use connector-code flow.

## Command variables

When a value belongs in the bot's own shell rather than an HTTP header, save it as a command credential. The bot calls `request_secret` with `"auth": {"type":"command"}` and no origin:

```json
{
  "label": "NetBird setup key",
  "purpose": "api_key",
  "credential": {
    "name": "netbird-setup-key",
    "auth": { "type": "command" }
  }
}
```

The name is exported to that bot's shell commands as an environment variable: upper case with hyphens as underscores, so `netbird-setup-key` becomes `$NETBIRD_SETUP_KEY`. The environment is loaded fresh before every command, so a variable added, replaced or removed mid-run applies to the next command.

A command variable overrides a space variable exported under the same name. That is accepted and owner-controlled: you decide which environment a bot's commands run in, and a per-bot value is the narrower choice, so it wins over the space-wide value it shadows. Remove the space variable, or rename the command variable, if you want the space value instead.

If a saved bot command variable cannot be loaded, that variable is unset for the command, even when a space variable has the same name. Other variables remain available; no credential value or load error is exposed.

A command variable is redacted from command output in its plain, base64 and URL-encoded forms, and it cannot be used with `secret_request` or a `browser_act` login fill. Names that change how a shell or a common runtime starts, trust TLS, or run git or ssh helpers are reserved, as are names beginning with `LD_`, `DYLD_`, `RAKAZO_`, `GIT_CONFIG_` or `NPM_CONFIG_`. The reserved list is not exhaustive: it covers the well-known variables, and saving a reserved name is refused with the reason.

**The bot's shell reads this value.** A command variable is a convenience for the bot, not a boundary against it: the shell command the bot runs, and the code that command starts, can print, encode or send the value. Redaction stops it appearing in a result the model reads; it does not stop a permitted bot, or anything the bot runs, from using it. There is no secrecy from the bot that was given the credential, so treat a command variable as shared with that bot and save only values you would let it use unattended, scoped to what it needs.

Command variables are managed in the same Vault as other reusable credentials. The request card a bot opens in a thread shows a command variable's variable name in place of a site.

## Saved website logins

When you want a bot to sign in to a website by itself, ask it to save the login. It calls `request_secret` with `"auth": {"type": "login"}`, the origin of the sign-in page, and the labels of the values the site signs in with:

```json
{
  "label": "Example sign-in",
  "purpose": "password",
  "credential": {
    "name": "example_login",
    "origin": "https://login.example.test",
    "auth": { "type": "login" }
  },
  "fields": ["ID number", "Phone number"]
}
```

Without `fields`, the card asks for a Username, which starts visible, and a Password, which starts hidden, as logins always have. A login has 1 to 8 fields, each with its own label. The card asks for one value per field, and a field the bot names starts visible only if every word of its label is an identifier word (ID, phone, email, account, username) or a plain filler word (number, name, address, last, digits), in English or Hebrew, such as "ID number" or "Phone number"; any other word, such as a password, PIN or code, or a misspelling, keeps it hidden, as does every label that isn't recognised. You can switch any field between hidden and visible before saving, and what you save is final: the bot names the fields but cannot send a visible flag, so the label is all it can influence, and the server only accepts an answer with exactly the fields the card asked for. All values are stored encrypted in the same way as other reusable credentials.

The card also has a **Save to Vault** switch, on by default, that only you can turn off. With it off, the login is kept encrypted for the run that asked for it and never goes into a vault. Only that run can fill it, on the card's HTTPS site, and it is hidden from tool output like a saved login. It is deleted when the run ends, however it ends, so a later run has to ask again. The site's cookies stay, so the bot may still be signed in.

To sign in, the bot fills fields found with `browser_snapshot`, naming each by its label:

```json
{
  "actions": [
    { "kind": "fill_secret", "ref": "e3", "secret": "example_login", "field": "ID number" },
    { "kind": "fill_secret", "ref": "e4", "secret": "example_login", "field": "Phone number" },
    { "kind": "click", "ref": "e5" }
  ]
}
```

`"username"` and `"password"` also name a login's first visible and first hidden field, so a bot can fill a login saved in settings without knowing its labels.

The backend decrypts the value and the page browser types it only if the page is still on the saved origin at that moment, so a login cannot be typed into another site or a page that redirected. The origin must be HTTPS: `RAKAZO_SECRETS_ALLOW_PRIVATE_HTTP` does not apply to website logins. A hidden field goes only into a password field, and a visible field only into a text, email or tel input. A visible field can appear on the page and in screenshots. A site's "show password" control still works normally; revealing a hidden value can make it visible in screenshots. Values travel to the computer over stdin, not command-line arguments. Snapshots never report the value of a field that holds a saved login. In every run, not only the one that filled it, tool results such as page results, command output and file reads are scrubbed of each saved login's hidden fields in plain, URL-encoded, form-encoded and base64 form; hidden values shorter than 6 characters are only scrubbed in the run that fills them. In the run that fills a login, page results are also scrubbed of its visible fields of 6 or more characters, which covers a site that echoes them in page text; shorter visible values are not scrubbed because redaction replaces every occurrence. Later runs leave visible fields readable, since one is often the user's own email address. Only this bot's own runs scrub its hidden fields: on a Team Computer, other bots' runs don't, so use a Private Computer for a bot that signs in to sites. A login cannot be used with `secret_request`. Fills need no approval: saving the login is the approval, and it is bound to one site. Use `forget_secret` to remove it.

Logins saved before fields existed read as a visible Username and a hidden Password, and fill exactly as before.

## Payment cards

A bot asks for a card with `request_secret` and auth `{ "type": "card" }`, with no origin. The card asks for the number, expiry, security code, name on card and, optionally, a saved contact whose address bills it. The whole card is encrypted like any other value. `list_secrets` shows the bot only its brand, last four digits, expiry, name and billing contact, never the number or security code.

The bot types a saved card with `browser_act` `fill_card`, passing `card` and `site`, the checkout page's HTTPS origin:

```json
{
  "actions": [
    {
      "kind": "fill_card",
      "card": "visa-4242",
      "site": "https://shop.example.test",
      "field": "number"
    },
    {
      "kind": "fill_card",
      "card": "visa-4242",
      "site": "https://shop.example.test",
      "field": "expiry"
    },
    {
      "kind": "fill_card",
      "card": "visa-4242",
      "site": "https://shop.example.test",
      "field": "cvc"
    }
  ]
}
```

Every call that types a saved card asks the person first, naming the card and the site ("Pay with Visa ·· 4242 on shop.example.test?"). Allow once is the only way to approve it, and a webhook run, which nobody can answer, is refused. One call types one card on one site, and the page browser types it only while the page is still on that origin, including a payment frame inside it. `postal_code` comes from the billing contact. Approving the card names no amount, so the click that places the order still asks, with the total the page shows; a call that types the card and presses that click asks once, showing both. That click counts against your [spending limit](./approvals.md#spending-limit), if you set one. Every run of the bot hides each saved card number from tool output, in plain, digits-only, spaced and dashed forms. The security code is not hidden, as for a wallet card: at 3 or 4 digits, hiding it would blank every total and order number that contains them.

## Contacts

A contact is a name, address, phone or email, the user's own or someone else's, such as `home`, `mom` or `office`. A bot asks for one with `request_secret` and auth `{ "type": "contact" }`, with no origin. A contact is not secret from the bot: `list_secrets` returns its fields, and the bot types them like any other text. It is still encrypted at rest.

## Managing the vault

Owners can manage what is saved without asking the bot. Open **Settings → Vault** on web, the
desktop app or mobile. It lists every item by its title, which the owner can change (a card without
one shows as "Visa ·· 4242", a login as its site), with a line from the item: a login's username, a
card's expiry, a contact's name and city. New adds a login, card, contact, API key or variable.
Opening an item shows its fields; protected values show only after you confirm it's you. From
there you can edit an item, add a note on when the bot should use it, which `list_secrets` shows
the bot, or remove it after confirming. Remove deletes the saved value immediately. Asking the bot
to `forget_secret` a name only removes it; it does not list or replace one.

A sign-in without a password, such as an ID number and phone number, uses the same login card. CAPTCHA and passkeys still use `request_takeover`, as does any sign-in you prefer to do yourself.

### One-time codes

When a site texts or emails you a code, the bot calls `request_secret` with `oneTimeCode: { "origin": "https://www.example.com" }` and shows a card, titled "Code for" that site's host, for the code. Only the person the run belongs to can answer it. The code is 4 to 12 characters, letters and digits in groups joined by single dashes, spaces dropped; anything else is refused. It is kept encrypted for that run only, never saved to the vault, and never shown to the bot: it types it with `browser_act` `fill_code` into one field on the page. Like a login fill, the page browser types it only while the page is on that exact HTTPS origin, and only into a text, email or tel input that looks like a code box (it says so, takes digits, is named or labelled like a code, or holds 4 to 12 characters). The field is drawn as dots, and so is the slot widget around it that shows the digits, and its value stays out of snapshots; slots drawn more than 50 ms late, more than three levels up, or after the page remounted them may still show in a later screenshot, and the masking may also cover a container that shows the same characters elsewhere. Dashes are dropped for a numeric box. A code is used once: it is claimed just before the page is asked, so two fills never both get it, and a fill the page refused gives it back. After a fill the page took, the code is kept only so the run goes on hiding it, in the forms a page might draw it (one digit per line, spaced, or dashed), and it is deleted when the run ends. A wrong or expired code needs a new request, which shows a new card. A code box that refuses the fill, such as one input per digit, a password-type or number-type input, or a field in a frame from another site, falls back to `request_takeover`. The code-box check is broad on purpose: another field on the same site named like a code, such as a promo or postal code, qualifies too. This needs a computer image that includes the code fill; an older image reads the fill as a password and types only into password-type inputs on that origin, so it falls back to `request_takeover` for a code box.

When the bot has its own email address and the site sends the code there, the bot usually does not need to ask. When it calls `request_secret` for a code, it first looks in its inbox, again once the card is saved (for mail that came while it was being saved), and again each time mail arrives while its card is open, for five minutes after it asked: a request's window runs from five minutes before it asked (or the start of its run, if that is later) to five minutes after, and mail outside it is not the request's. Mail does not say which sign-in it is for, so on every one of those looks, and for connected mail as for the bot's inbox, an email answers a request only while that is the one open code request it could be for: while another request for a code on the same site is open (asked and not yet answered, whether or not its card shows yet) in a run that is still going and whose codes can be in the same mail, which is any other run of the bot, whoever started it, and any run of the bot's owner, in whichever of their bots and Spaces, an email that arrived in that request's window answers neither, and the cards stay for the owner. Only such a request counts: one for another site, one for a password or a key, one whose run ended, one whose run started after the email came, and one that asked more than five minutes before or after the email came block nothing, so a card left open for an hour keeps no other request from the site's mail. A request the bot's tool call is working on at that moment, whether it is still looking for its code or already using its answer, counts as open. That is decided in the transaction that takes the code, so two runs that ask at the same moment both get the card. Code requests for pages whose address holds the site's name are read for this, up to 100 of them that are open and asked within five minutes of the email; with more, they are not all compared and the card opens. A sign-in whose run has not asked yet is not known to the server, so an email that came before it asked can still be taken by another run. It uses a code only when all of these hold: the run may read the inbox (the owner's own run, not one started by another bot's message, in a group, or in a chat that reaches other people); the page is HTTPS, and the run's own browser reports the page on that exact origin when the bot asks (an origin the bot names is not enough, written with or without a trailing slash or a default port, and with no computer running or no page open the card opens); the page's site is not a public mailbox domain (gmail.com, outlook.com, yahoo.com and the others the app knows), where anyone with an address can send mail signed by the site; the email arrived in the request's window (after the run started, and no more than five minutes before or after the request), and after the last time another code request for the site was answered in any run of the bot or of its owner, in any of their Spaces (the owner may have typed that email's code into any of those cards; answered here means no longer open, whether the owner typed a code, mail answered it or it was dismissed, and the time compared is when the card was answered, which the answer records, or, for a request closed any other way, when it last changed; a request for another site or for something other than a code says nothing of the email); it passed its sender's signature check, was sent to the bot, was not sent by the bot or by any bot on this server's mail domain, and is known not to have come through a mailing list (a `List-Id` or `Precedence: list` header) and not to be an auto-reply or bulk mail (an `Auto-Submitted` value other than `no` or `auto-generated`, an `X-Autoreply` or `X-Autorespond` header, or `Precedence: bulk` or `junk`), as either can carry what someone else wrote (mail saved before this release told these apart is never used); its sender's site is the page's, where a site is the registrable domain and each customer's domain under a shared hosting suffix (such as `victim.duckdns.org`) is its own site (mail from `example.com` for `login.example.com`); its subject and text hold exactly one code, of 6 or more characters or with letters; and no run has taken a code from it yet. Emails from the site that name no code are skipped, so a newer welcome email does not hide an older code; if the remaining emails hold different codes, none is taken. An email from the site that names a code but gives none to take (it holds two, or one of 4 or 5 digits, or calls a code old or expired as below, or names one and is longer than is read) leaves the site's other codes in doubt: while one is in the window, no code is taken from the site's mail, in the bot's inbox or in a connected mailbox, and the card opens. Only mail that could itself answer counts for this: unsigned mail, mail from another sender, mail that arrived outside the request's window and mail from before the last answered code request for the site change nothing. An email with a sentence, however long, that holds a code word and a word saying a code is old, previous, expired or invalid (past forms only, so "expired" but never "expires"), in any language the app reads codes in (English, German, Spanish, French, Dutch, Polish, Portuguese, Russian, Turkish, Hindi, Hebrew, Japanese, Korean and Chinese), gives nothing, even when it also names a current one, and whatever else that sentence says: "Enter this code on the previous page" gives nothing too, and the card opens. A sentence, for this, ends at sentence or clause punctuation, a bracket, a quote, a pipe or a blank line; a line break inside a paragraph does not end it, as mail wraps sentences over lines. Such a word in another sentence or paragraph ("Your previous orders are below.") is about something else and changes nothing. Words are matched in any case, the same under every locale: accents are composed first, and the Turkish dotted capital İ and dotless ı read as i. A number counts as a code only when the sentence or line it stands in is written in one of a few fixed forms: a code word (code, passcode, OTP, 2FA, one-time password, or the same word in one of the app's languages), then an optional colon, equals sign or dash, then the code ("Your verification code is 482913", "Code: 482913"); the code, then the code word ("482913 is your sign-in code"); or a line that only names a code ("Your code:", or the subject) right over a line holding nothing but the code. Around the code word and between it and the code only a short fixed list of words per language is allowed: the little words such a sentence has (your, is, enter, to sign in) and sign-in qualifiers (verification, security, one-time, confirmation, login). Anything else in that sentence, another number of any length, a word the list does not hold, or a noun that makes the code word name something else (tracking code, code de suivi, order, ZIP code, promo code, QR code, country code, error code, code postal), means the sentence gives nothing: the word next to the code word has to be on that list, so no list of nouns to deny is kept. A bare PIN is not a code word, as it names a postal area in some countries. Each sentence is read on its own, so "Order 48213977. Your code is 731905" gives 731905, while a number alone on a line with no code word right over it, a code on a line over its code word, or a code in brackets gives nothing. A sentence longer than 200 characters gives no code, though it is still read for the words above. Of a subject or a text longer than 20,000 characters, which is where the inbox cuts a body, only the first 20,000 are read, and the email gives no code: what was not read could say the code expired or name another. When what was read names a code, it is an email that names a code it does not give, as above; when it names none, as a long newsletter does, it is skipped like any email that names no code. More emails fall back to the card than a looser reading would allow; that is the point, as a wrong number costs a sign-in attempt. A code is 4 to 8 digits, two equal groups of 3 or 4 digits split by a space or a dash, or 6 to 8 capital letters and digits with both. A number is skipped when a letter, digit, `$`, `€`, `£`, `¥`, `/`, `\`, `@`, `%` or `_` touches it on either side, when `#`, `+`, `.`, `,`, `=`, `&`, `?` or `-` comes right before it, when `.`, `,`, `:` or `-` comes between it and a letter or digit after it, or when a digit is one space away, or one dot or dash before it (Chinese, Japanese and Korean letters may touch it); so is a 4-digit number from 1900 to 2099. A 4- or 5-digit code is never taken, and the card opens: hiding it would mean hiding that bare number in everything the run reads, which would blank years, prices and other short numbers too. It still counts as a second code. Taking an email's code is a database claim on the message (its sender's signature, which a copy delivered again after the bot deleted the email shares, and so does the same message in another mailbox, the owner's connected one included), made in the same transaction that stores the code and records the answer: the card's, as the owner's typing it would, or, for a request no card was shown for, what `request_secret` returns. So when that fails the email stays for the next look, a request cut off right after gets that answer when it is retried, and a request settled meanwhile keeps nothing: the message gives its code to one run, even when two runs or a run and arriving mail look at once or read it in different mailboxes or Spaces (the claim's key is the message alone, with no bot, mailbox or Space in it), and a run takes at most one emailed code per site; after that the card opens for the owner. The same transaction asks again, of every Space, what the look asked: whether a code request for the site was answered since the email came, and whether another open request could take it. While it does, no code card of the bot or of its owner can be answered, and an answer already under way is waited for: the two take the same lock, so a code is taken either before a card was answered or knowing that it was. Besides the claim itself, which is found by its key, those two questions are the only reads this feature makes outside the run's own Space: one named system read (`packages/db/src/code-requests.ts`) that looks at the code requests of the bot's runs and of its owner's runs and returns yes or no, nothing else. Each reads at most 100 code requests for pages whose address holds the site's name; past that its answer is yes, and the card opens. The sender is encrypted, so the inbox is asked only for mail that holds the words of the site's name, through the index of hashed words its search uses (mail not yet encrypted is asked for by its sender's address; for a site with an internationalized name, which can be written in two ways, all mail in the window is asked for). What that finds is read newest first in batches of 50 and each sender checked, up to 500 of the site's emails in the window and 5,000 emails that name the site in all (signed mail that is neither list nor bulk mail and arrived in the window, which is at most ten minutes long), past either of which the card stays for the owner. Mail that does not name the site is neither read nor counted, however much there is, and mail from other senders does not hide the site's. Only the site's emails no run took a code from are read in full. A notice marked `Auto-Submitted: auto-generated` (or carrying `X-Auto-Response-Suppress`) is still used: that is how sites mark a notification sent to one person, sign-in codes included. A site that marks its codes as bulk mail gets the card. These headers are not signed, so they only ever make mail count for less. The code is then stored and typed exactly as one answered on the card would be, and the page browser again types it only on that exact origin. A request it answers shows no card and sends no notification; a card it answers looks answered by the owner, and the run goes on. A card the owner answered first stays answered, and the email does nothing. Otherwise the card opens as before, and the owner can still answer or dismiss it; so does any failure while looking (the inbox or a connected mailbox cannot be read), with only the error's name in the log, and a failure while answering an open card from arriving mail never fails that mail's delivery. That covers a site that sends from another domain, a code sent by text message, an email with two codes, mail that came while the inbox was over its daily limit, a run that may not read the inbox, and any other run's card. The email itself stays in the inbox with the code in it. From the moment the server takes the code, `read_email` in that run hides it in every email it returns, in every field but the email's id and time (sender, recipients, subject, text, preview and file names): in the same forms as a typed code, and as its characters in order with any run of spaces (no-break, zero-width and other Unicode spaces too), line breaks, dots, dashes or middle dots between them. Which codes the run holds is asked as each result is produced, not when the call began: once an email read by id has been loaded, and for a list, a search or a wait as every look starts and again as it ends. A look during which the run took a code is dropped, with how far the call had read, and made again as a call that began holding the code would make it, at most three times; past that the call returns an error asking to try again. A look that starts after the code was taken never has the database match the search. So a wait that began before the code was taken neither shows it nor matches a search on it, and each time the run's codes are asked for, every form of them is added to what the rest of the attempt hides. A request that keeps a code adds it to what its attempt hides before the transaction that keeps it commits; if keeping it then fails, it stays hidden for the rest of that attempt. In a run holding such a code, a search reads up to 1,000 emails in its time range itself, newest first (with `since`, oldest first; a later look of a wait starts 23 seconds before the newest email it read and leaves out the ones it read, so mail saved late still turns up), and matches only the text after hiding, each piece between hidden spans on its own and the `[redacted]` mark left out, so a search that would match only the hidden code, or the mark itself, returns, `nextSince` included, exactly what a search for text found nowhere returns. In such a run `read_email` also gives the run no attachment from any email, listing each file as unavailable: a file could carry the code in a form that cannot be hidden. Any other run searches the database as before. While a code row of a run that took a code from an email cannot be read (the secret store is down, or a key is wrong), no attempt of that run starts (the setup is retried, as any setup failure is), `read_email` in a running attempt returns an error asking to try again, and `request_secret` keeps the row as a spent code, still hidden once it can be read, instead of deleting it: any email might hold the code, so none is shown until it can be hidden. The `[redacted]` mark shows where the code was, as it does when the email is read. A background helper the run starts cannot use `read_email` or `request_secret`. That is all it guarantees: an email the bot read before the code was taken was already seen, including one in a routine's prompt, the files of an email it read by id before then are already on its computer, and the bot can still read new mail as it arrives with `read_email` `waitSeconds`. The tool descriptions tell the bot to use `request_secret` for a code it must type into a page.

The owner can also let a bot take the code from the email they connected to Rakazo themselves, with the bot's "Fill sign-in codes from my connected email" switch, off by default. Only the bot's creator sees and sets it, since it reads their mail; a bot that comes to exist any other way (created, duplicated, imported from an account archive) starts with it off. While that is on (checked again at the start of each look, so turning it off stops a running attempt too), a `request_secret` for a code that finds no code to take in the bot's own inbox reads (an inbox holding the site's emails with different codes, an email of the site's that names a code it does not give, or more mail than it reads, keeps the card), in each email connection the owner made in that Space that is connected now and names the one account of the provider it is to read, the up to five emails from the site in the same window as the bot's inbox (after the run started and no more than five minutes before or after the request), once when the bot asks and once more after the card is saved. A connection that names no account (connections made long ago store only the provider's name) is not read at all: the provider would choose one of the owner's accounts itself, which could be a mailbox that was never connected in that Space, so the card opens until the owner connects it again. Which connections are read is asked afresh on each look, so one that was revoked, removed or has expired at the provider since the last look is not read. The provider's search by sender is loose (a name or another domain holding the site's domain matches), so the mailbox is listed page by page, newest first, five messages a page, and each listed message is first asked about without its content: who its From header names, how large it is and when it arrived. The messages of a page are asked about together, so mail the search matched from other senders costs the look one call's time a page. A message another sender sent is never fetched and counts for nothing, however large it is and however many there are; neither does one that arrived outside the window or before the last answered code request for the site. Only a message that may be the site's (its listed sender is on the site, or the provider tells no sender, or tells anything but one plain address) is fetched. At most ten pages are listed, and a sixth email from the site itself or an eleventh page opens the card; mail arriving later does not answer the open card, so the owner answers it or the bot asks again. The bot's own inbox is looked at first, and a site's code is filled once per run across both. Each email is held to the same rules as one in the bot's inbox: it must pass its sender's signature check, be addressed to that mailbox, not come through a mailing list nor be an auto-reply or bulk mail, come from the page's site, which is not a public mailbox domain nor the mailbox's own domain (where anyone with an address there can send it signed mail), have arrived in that window and after the last answered code request for the site in any run of the bot or of its owner, in any of their Spaces, and hold exactly one code (an email of the site's there that names a code it does not give opens the card, as in the bot's inbox); a message answers one run only, whichever mailbox or connection to it reads it; and, by the same claim as for the bot's inbox, it answers no request while another open code request for the site could be the one it is for. Only the owner's own connections are read, only in a run that may read the bot's inbox, and only with read calls: the provider's profile, a search by sender since the exact moment the window opens, each listed message's headers and size, and the raw message of those that may be the site's. A look fetches at most 2 MiB of mail from the connected mailboxes in all, and only the messages it fetches count toward that. A message that may be the site's is fetched only when the provider says it fits what the look may still read; what comes back is held to that by its encoded length before it is decoded, and again before it is parsed. One that does not fit, or whose size the provider does not tell, is not fetched and opens the card, as it may be the newest from the site; so does mail from the site past 2 MiB in all. The listed sender is what the message's From header says, which anyone can write, so it only ever rules a message out: one that is fetched still has to pass the signature check, and mail that only claims to be the site's and is too large to fetch opens the card without any code being taken. The parser itself refuses a raw message over 25 MiB, whoever hands it over. Nothing from the mailbox is stored or logged; each mailbox read is recorded in the audit log (the bot, the run, the connection, the site and whether the read worked, never what the mail says); a listing in a shape that cannot be read or longer than asked for, a listed message without an id or that the provider cannot be asked about, a message that may be the site's whose arrival time is not told or that cannot be read, a signature that cannot be checked for now, or a read that takes more than three seconds, opens the card (never another message answering for what was not read), with only the error's name in the log. A code taken this way is hidden in `read_email` as one from the bot's inbox is; a connector tool that reads that mailbox returns the email as it is, code included, as it could before the code was taken. The connection's grant is whatever the provider gave when the owner connected it, which is usually wider than reading; this feature uses only the read calls above, so an owner who wants a narrower grant should connect a mailbox used for nothing else. The run that holds the code is the only one that hides it; another run, or another bot, that reads that email sees the code as it does one the site sent to the bot's inbox.

The value is typed into a real browser on the bot's computer. Anything that can read that browser, including the bot's own shell commands through the page or its debugging port, could read a filled field. Keeping the value out of model input stops accidental disclosure, not a bot that sets out to extract it. Save logins only for accounts you would let the bot use unattended.
