# 加密消息中文搜索对比实验

在这组短消息里，现有前缀、中文分词、相邻双字分别找回 **27/52、49/52、50/52** 个应命中的查询–消息对。查「部署」，现有前缀找到 3 条，两种候选方案均找到全部 6 条，包括「我们今天讨论部署方案」和「今晚部署API服务」。

### 怎么比较

- 每条消息只有一个文本块。三种方案复用产品的前缀编码和 HMAC 函数，共用同一个合成测试密钥。对比脚本固定了实验时的三种切分规则，其中「现有前缀」指双字方案接入前的基线。计入完整的 `searchTokens` 数组，包括历史检索使用的整词标记和块类型 `text` 的前缀标记。
- **现有前缀**直接对产品取出的连续字母数字串建前缀。**中文分词**在汉字与其他字母数字的交界处分开，再用 `Intl.Segmenter("zh", { granularity: "word" })` 切连续汉字，对每个词建前缀。**相邻双字**在相同边界内，按 Unicode 码点滑动，每次取两个连续汉字。两种候选都对非汉字的字母数字串沿用原前缀规则。三种方案的写入与查询采用各自相同的切法。
- 人工标出每个查询应该找到的消息，并用产品的 `matchesSearchQuery` 核对全部 644 种组合。判断依据是正文包含输入的连续文本，忽略大小写。因此「市长」应该找到「南京市长江大桥」，而「API 服务」只匹配保留该空格的写法。
- 在内存中按数据库的包含条件筛选候选，要求一条消息具备查询的所有标记，再用原文复核。如果查询生成零个标记，按 API 的规则扫描最近最多 200 条加密消息。23 条样本均在窗口内，也都能放进一个候选页。下表将直接经索引找回的结果和靠扫描找回的结果分别计数。

### 实测占用

将各方案生成的标记原样写入 PostgreSQL 17.5（PGlite 内存实例）的 `integer[]` 列，写完全部 23 条后分别创建 GIN 索引。数组列用 `sum(pg_column_size(tokens))` 测量，GIN 主文件用 `pg_relation_size` 测量。

| 方案     | 标记数 | 纯标记载荷 | 数据库内数组合计 | GIN 主文件 |
| -------- | -----: | ---------: | ---------------: | ---------: |
| 现有前缀 |    353 |    1,412 B |          1,895 B |     16 KiB |
| 中文分词 |    256 |    1,024 B |          1,507 B |     16 KiB |
| 相邻双字 |    367 |    1,468 B |          1,951 B |     16 KiB |

中文分词的数组较现有前缀节省 388 B（20.5%），相邻双字多用 56 B（3.0%）。三份 GIN 都只分配了两个 8 KiB 页。这组数据能区分数组开销，更大消息库的 GIN 增长率仍待测量。

### 哪些查询拉开了差距

- **普通词和中英紧邻。** 搜「讨论」时，现有前缀漏掉全部 3 条，两种候选均通过索引找回。搜「部署API」，两种候选都找到了没有空格的 M04，原文复核也正确排除了有空格的 M05。
- **跨词输入。** 搜「市长」，ICU 在正文里切出「南京市 / 长江」，查询却切出「市长」，只有相邻双字找到了 M17。搜「论部」，ICU 将查询切成两个单字，触发最近消息扫描，找回 M01 和 M23。相邻双字直接命中两条。另一个触发扫描的查询「海」在三种方案中都要扫描。中文分词一共检查了 46 条扫描候选，另两种各检查 23 条。
- **英文词内部。** 三种方案都漏掉了 `PostgreSQL16` 里的 `sql16`（M07、M08），均能通过复核排除次序颠倒的 `BUILD … run` 对 `run build` 的干扰。

若按当前产品的字面包含规则取舍，这批样本中，相邻双字的索引直接找回了 48 个应命中对，中文分词直接找回了 45 个，分词的优势是数组最小。结果来自有意覆盖边界的合成样本，未按真实查询频率加权。三方案对比阶段使用独立的合成索引，当时未运行旧消息回填。

### 生产实现与旧索引兼容性

同一批 23 条消息走实际的索引写入与查询函数，52 个应命中对中找回 50 个，其中 48 个通过索引找回，2 个通过短查询扫描找回。生产实现为每条消息保留全部旧前缀，新增双字和拆出的非汉字前缀使用独立的 HMAC 输入。这样，原本只搜词首的候选窗口仍然只接收原词首命中。最终共写入 **600 个标记**，载荷 2,400 B，PostgreSQL 数组共占 **2,910 B**，GIN 占 **40 KiB**。与旧格式相比，数组增加 1,015 B（53.6%）。未发生中英紧邻切分的消息复用原有非汉字前缀。

生产方案也给汉字与字母或数字交界处紧邻的两个码点建标记，与连续汉字的双字共用 251 个名额。修复前，查「署A」漏掉「部署API」。PostgreSQL 回归现可从「已经部署API服务」找回「署A」「I服」和从英文词内部开始的「PI服务」，同时排除有空格的写法。全角数字与补充平面汉字相邻的「９𠮷」也能命中。最终原文复核区分全角和半角，纯英文词内的 `sql16` 仍沿用原有前缀规则。

最初实验也测了在同一个编码域同时写入全部旧前缀和新增标记的成本。去重后有 536 个标记，载荷 2,144 B，数组共占 2,648 B，GIN 占 32 KiB。相比旧格式的 1,895 B，这使样本的数组多占 753 B（39.7%）。同域双写会把消息内部的双字当作原词首，密集的误候选可能把原有命中挤出搜索窗口。

另一组兼容检查用固定种子生成 400 条包含中文、英文、全角字母、数字、标点和补充平面汉字的消息，每次从生成该消息的字符中截取一个查询。共 8,727 次非空查询。其中 3,595 次通过旧索引的候选条件，新查询对原格式和重新索引后的消息均保留了这 3,595 次匹配。另有 1,328 次旧查询没有可用标记，新查询也都保留了有限窗口扫描。两者合计 4,923 次。短查询检查验证的是选择扫描的条件，实际结果仍取决于消息是否在最近 200 条的窗口内。

兼容检查还对原实现产生的存储标记和查询标记计算 SHA-256 指纹，确保复跑时比较的是同一批旧编码。

对超过 251 种不同双字的消息，写入端会把整条消息的双字映射到 251 个桶，再对出现的桶计算 HMAC。251 是小于 256 的质数，使连续码点能分散到不同桶，同时把新增双字标记的载荷限制在 1,004 B。整词、原前缀和非汉字前缀另外计入。查询用同一规则计算所需的桶，再解密候选核对原文。对 200、500、100,000 字的连续汉字分别搜索只出现在末尾的「鲸落」，三个样本均命中。三者完整数组分别含 212、264、264 个标记，旧格式均为 13 个。

私聊和群聊各自为原前缀及明文候选保留原有的 500 个名额，再分别为精确双字或拆出的前缀、长消息的桶各取最多 500 条候选。各窗口先排除已被前一条件覆盖的行，按时间合并后解密核对原文。包含很多种双字的消息可以占满所有桶，较旧长消息仍可能落在桶候选窗口之外。

PostgreSQL 18.7 的两项窗口回归覆盖了不同干扰。第一项在旧消息之后写入 501 条填满所有桶的误候选，再写入一条末尾含有「鲸落CDN」的消息，查询返回了新旧两个命中。第二项在旧消息「归档期限 归档 期限已定」之后写入 501 条「确认归档，存档期限」。查「归档期」或「归档 期限」都只找到旧消息，重建该消息索引后结果相同。

API 的分页回归给私聊和群聊分别提供 205 和 310 个候选 ID。每个范围只执行一次候选窗口查询，之后每次读取最多 100 条当前消息。两个范围的第一页都在读取前消失，第二页原文不匹配。第三页分别贡献 2 和 23 个结果，填满后不再读取群聊第四页。

在移植到当前主线之前，与搜索、加密及历史检索相关的 86 项单元测试和 PostgreSQL 18.7 的 34 项集成测试通过。API 回归先在旧实现上复现了混排消息漏搜，再在新实现上验证同一查询能返回两种索引格式的消息。
