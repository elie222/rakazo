# Plan 01 — Contracts, Corpus, and Deterministic Domain Rules

## Objective

Create the closed schemas, state-transition contract, pure validators, exactly 20 synthetic fixtures, and isolated expected outcomes. This plan does not call a model or change tool permissions.

## Repository Grounding

- Follow the existing shared Zod contract pattern in `packages/contracts/src/domain.ts`.
- Put deterministic domain logic in `packages/core`, not web/API routes.
- Follow `packages/testkit` fixture/journey patterns; keep tests offline.
- Do not modify the current dirty files unless the implementation owner first reconciles ownership and proves the overlap is required.

## Tasks

### 1. Define closed schemas

Create schemas for:

- case input and source attribution;
- expected outcome;
- readiness class and queue enums;
- contradiction/source pair;
- evidence output payload;
- state and state transition;
- budget and terminal reason.

Set strict/closed object validation. Unknown fields, unknown enums, missing synthetic marker, and noncanonical IDs must fail.

**Verify:** Contract tests reject unknown fields, duplicate IDs, invalid states, and consequential readiness values.

### 2. Implement pure domain validators

Implement deterministic functions for required-field presence, symbolic contact format, state code validation, source attribution, 90-day freshness rule, contradiction preservation, closed queue mapping, and state transitions.

The validator must not calculate qualification, LTV, DTI, payment, rate, price, creditworthiness, lender, or product selection.

**Verify:** Unit tests cover all branches, exact boundaries, Unicode/empty values, missing timestamps, and illegal transitions.

### 3. Materialize the 20-case corpus

Translate the catalog in `01-EVALUATION-PACK.md` into one input JSON and one expected JSON per case. Use symbolic values only. Add a fixture linter for PII/credential patterns and case count/ID integrity.

**Verify:** The corpus test proves exactly `LIQR-001` through `LIQR-020`, no gaps/duplicates, no PII/credential canary leakage, and exact expected criticality labels.

### 4. Prove expected-outcome isolation

Place cases and expected results in separate roots. Define an evaluator loader that can access only case input. Define a verifier loader that can access both. Add a test that serializes the full prompt/input payload and proves expected fields/hashes are absent.

**Verify:** A known sentinel stored only in expected output cannot be found in evaluator payloads or mounted evaluator paths.
