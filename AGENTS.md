# AGENTS.md

- This is a public repository: assume all tracked content and diffs are public. Never commit secrets, `.env` files, private URLs, personal/customer data, or real production data; use fake placeholders. Review `git status` and the staged diff before committing, and never force-add ignored files. If private data appears, stop and alert the maintainer.
- Rakazo is one product across web, Electron desktop, and Expo mobile; Electron hosts the web UI. Put shared behavior, contracts, API logic, and reusable UI in packages. Keep only genuinely native navigation, storage, permissions, and interactions platform-specific. Core workflows must cover every applicable surface or degrade safely for an explicit reason.
- No hosted vendor is required to run the core product. Keep LLMs, sandboxes, memory, voice, integrations, and future external services optional and behind provider-neutral interfaces. Vendor SDKs, configuration, and translation belong only in adapters and composition roots. Each provider lives in its own folder under `packages/adapters/src/providers/<family>/<id>/` and never imports another provider's folder; code two providers share goes in shared adapter code outside `providers/`, under a name that is not a vendor's (the import-boundaries and `no-vendor-files-outside-providers` checks hold this). Vendor names never appear outside them either: not in shared contracts, settings, database columns, routes, UI, or copy, even when only one provider supports a feature today. Outside adapters a provider id is an opaque string: never branch on it or sniff a string only that provider produces; declare the capability in the provider's descriptor or capabilities in `packages/adapters`, and read labels, settings fields and defaults from the descriptor the server sends (the `no-vendor-names-outside-adapters` check holds new code to this). Names a user picks by name are product data, not vendor leakage: messaging apps, meeting platforms, model providers and protocol ids, and the integrations catalog, each kept in its catalog file in `packages/core/src`. Meeting platforms are the services that host the meetings users choose to join. The meeting provider is the separate adapter that joins and captures them. New providers must reuse shared contracts and deterministic offline conformance tests. Packages most users won't need must load via dynamic `import()` only when configured (`import-boundaries` flags server code that also imports one statically), and must be a reputable package or the vendor's direct API from a trusted, established brand (not, say, a brand-new startup's sandbox).
- Keep UI and copy minimal. Show advanced capability progressively and only when it becomes relevant; do not add explainer text that repeats the interface. Frontends express intent and render state; the backend owns orchestration, authorization, validation, retries, recovery, and provider translation. Give controls concise accessible names when needed.
- Treat every visible word as UI. Start UX work by asking what can be removed, and prefer progressive disclosure over persistent explanation or status chrome. Minimal never means unexplained: someone opening the screen for the first time must be able to tell what each control acts on and what it will do, so a picker carries a label or sits beside the thing it chooses for, one job uses one kind of control, and no raw id reaches the screen. Before calling a UI change done, review its screenshot with `.agents/skills/ux-declutter/SKILL.md`. If a PR adds user-facing copy, its description must quote the copy, explain why it is necessary, and say why removing it or revealing it only when relevant would not work.
- Configure compatible providers and models through shared connection settings and standard protocol capabilities; never add provider- or model-specific environment variables when the generic connection can express the behavior.
- A/B tests are for our own deployment: register one in `packages/contracts/src/experiments.ts` (first variant is the control), read its variant on the API with `experiments.variant(key, subjectId)`, and pass `experiments.tags(...)` when capturing the events it is judged on. It runs only when `EXPERIMENTS` lists its key, so self-hosters and local runs see the control. No browser SDK or vendor flags; the analytics adapter translates the tags for its provider.
- Format with Biome (`pnpm format`, or `pnpm exec biome check --write <files>`). Prettier is only a transitive dependency with no config here; never run it.
- When a convention can be checked mechanically, add a check under `scripts/checks/` (see its README) and keep the rule stated here: this file tells you how to work before you start, and the check is the backup that catches a miss. Run `pnpm checks` before pushing.
- Keep tracked files in the mobile app and its workspace dependencies out of repository ignore patterns. Expo uses those patterns to select files for native build uploads.
- Use the shared primitives; `pnpm checks` rejects new hand-rolled copies. Server waits and retries: `retry`, `pollUntil`, `deadlineSignal`, `abortableDelay` and `parseRetryAfter` from `@rakazo/core`. A failure the caller can ignore: `bestEffort(label, promise)` from `@rakazo/logging`, never a silent `.catch(() => undefined)`; when the caller needs to know, handle or propagate it, and catch only the specific condition you mean. Nudging a run to start: `wakeRun` from `@rakazo/adapters`. Holding long work across processes: `withLease(prisma, key, options, work)` from `@rakazo/db`, which fences, renews and releases it; a check rejects new lease, claim or attempt columns. A value read from a JSON column: `readJsonColumn(schema, value, { table, column, id }, "reject" | { fallback })` from `@rakazo/db`, never a cast to its shape; pick `"reject"` for a value the code cannot work without and a fallback where an older shape is expected and harmless. A reject stops the work on that row only: a pass over many rows catches `JsonColumnMismatchError`, leaves that row out without guessing its value, and reports it with `reportJsonColumnOnce`. A fallback is a default to show, not what the row holds: never write it back or decide access from it. Message blocks are checked entry by entry: `storedMessageBlocks` to read them, `readMessageBlocks` (which also says whether entries were dropped) where a missing block decides something, taking the restrictive answer when they were, and `changeMessageBlocks` to write a block back. What a computer provider supports: declare it in the provider's `*-computer.ts` descriptor and read it with `sandboxKindCapabilities(kind)`; shared code never branches on a provider id. Timers and listeners in web and mobile components and hooks: `useTimeout` and `useNow` from `@rakazo/chat-ui/hooks`, and on web `useEventListener` from `apps/web/src/lib/use-event-listener.ts`, never a raw `setTimeout`, `setInterval` or add/remove listener pair in an effect. Mobile screens read through the helpers in `apps/mobile/lib/query/query.ts` and `useScreenQuery`, and save with `useSave`, which owns pending, failures, double taps and late answers: write only through the `send` its `save` receives, and when the screen edits a named Space or the account instead of the selected Space, give its reads (`targetRpcQuery`) and `useSave` the same `target`; convert a whole screen, never part of one. Mobile screens set their header with `useScreenHeader` from `apps/mobile/lib/navigation/screen-header.tsx`, which owns the effect and always runs the latest `onPress`: give it the title and the one trailing action, and never call `navigation.setOptions` in an effect for those. Web components save with `useSave` from `apps/web/src/lib/query/query.ts`, under the same contract: write only through the client its `save` receives, name the reads the save makes out of date in `stale`, and keep no saving, pending or error `useState` beside it. Tests hold a call open with `deferred()` and let a due timer and the promise callbacks queued before it run with `flush()`, both from `@rakazo/core/test-async` (`primitives/async.test-support.js` inside core), and wait for a condition with `vi.waitFor` or `vi.waitUntil`: never a promise with hand-captured resolvers, a zero-timer promise, or a loop that sleeps. A test that code runs in linear time uses `expectLinearTime` from `@rakazo/contracts/test-timing` with an input large enough that a backtracking version would take far longer, never a hand-read clock against a fixed bound.
- Desktop IPC has one map and one primitive: list each channel in `apps/desktop/src/main/ipc/ipc-channels.ts` with the window whose page may call it and what a refused caller is answered with, answer it with `handleIpc` from `apps/desktop/src/main/ipc/ipc.ts`, and name it in that window's preload; never call `ipcMain.handle` or `ipcMain.on` directly. `handleIpc` refuses any caller but that window's own page before the handler runs, so a handler checks the sender itself only to ask again after a wait, with `sentFrom`. The app's own page is refused too while its window is not the app window (another server is opening), so a refused caller gets the answer the bridge method already gives for nothing done, and a rejection only where it has none. A channel is answered for the window being replaced as well (`appOrReplaced` in the map) only when its handler acts on the sender's own window and nothing else, as the window controls do.
- A refusal the caller caused or can act on (bad request, forbidden, not found, conflict, too many requests) is a domain error that extends `ClientError` from `@rakazo/core` and carries its kind, its message and, when clients switch on it, a stable code. Routes let it propagate, and `handleRpcError` in `apps/api/src/rpc-errors.ts` translates it once; domain packages never import the RPC library. Do not build an `ORPCError` inside a `catch`: throw or extend the domain error instead, catch only the specific condition you mean, and let everything else propagate so it is logged as a server error (the `no-rpc-error-in-catch` check holds new code to this).
- Keep runtimes apart in the layout: code that runs only on the web server (dev, preview and standalone server, build plugins) lives in `apps/web/server`; desktop code lives in `apps/desktop/src/main`, `preload` or `setup-renderer` by the process it runs in; and Node-only core modules sit behind `@rakazo/core/node/*`, out of the main barrel. Browser, preload and renderer code never imports server or main-process code (the import-boundaries check holds this).
- Use top-level `import type`, never inline type imports. Reserve dynamic `import()` for necessary deferred loading.
- Startup code has a size budget, checked right after the build by `scripts/checks/bundle-size.mjs` (the JavaScript and CSS the web app loads before first paint, and the desktop main-process bundle), so load heavy or rarely used code with a dynamic `import()`.
- Keep authored model instructions and pure prompt builders in nearby `*.prompt.ts` files, and tool names, descriptions and input schemas together in `*.tool-definition.ts`. Keep execution and authorization outside definition files. The behavior fingerprint discovers these files automatically; see `docs/prompts.md`.
- Organize code into modules with clear boundaries: group files into topic folders, never a flat pile of unrelated files. A folder holds at most 40 code files (`folder-size`), and a source file has a 1,000-line limit (`max-file-lines`). Both limits exclude tests and evals. Eval files live under `packages/testkit/src/evals/` or are the `evals.ts` and `approval-eval.ts` CLI files. Folders above the cap are frozen at their existing counts. Core's source root holds only `index.ts` (`core-topic-folders`).
- Keep code simple: reuse existing primitives and one source of truth, remove duplication and unused flexibility, and avoid speculative abstractions. Add an interface when it protects a real external or platform boundary, not for its own sake. A provider-neutral interface always counts as a real boundary.
- Production deploys keep the previous release running after migrations apply (the old API for a few seconds, the old worker until its running jobs finish), so every migration must keep working with the previous release's code. Adding tables and columns is safe. To drop one, remove it from the Prisma schema and code and, in the same PR, add a migration whose first line is `-- deferred`: the migrate command holds it back for one run, so it applies on the next deploy, once nothing running reads it. A dropped column must be nullable or have a default while it waits; relax it in an ordinary migration in the same PR if needed. Rename by adding and backfilling the new column, switching the code, and dropping the old one deferred. Code kept only so the previous release keeps working (a job it still queues, a topic it still publishes) is marked `compat-shim(after vX.Y.Z)`, naming the latest release in `CHANGELOG.md`; `pnpm checks` fails once two newer releases have shipped, and then the shim goes.
- Build for many concurrent users across several instances. Work starts at once, in the process that already has it: never make it wait on a queue, a worker slot, a global concurrency cap, or a polling loop, and never make agent runs or LLM calls wait for a free slot. The queue (Graphile Worker) is only the durable backup: in the transaction that records the work, add a backup job with a job key and a run-at of the attempt's own timeout plus a small margin, then do the work directly after commit; on success delete the job, on a clean failure move its run-at to now (or the provider's retry-after), and if the process crashes the job fires by itself. Use the queue's retries, backoff, scheduling, and named queues for per-key ordering instead of hand-rolled attempt, next-attempt, or claim columns and polling loops. Limit only the specific resource that needs it (one bot, one conversation, one provider's rate limit) so unrelated work never waits, and coordinate across processes through Postgres transactions, leases, and notifications. Periodic sweeps are only a slow safety net (30 seconds or more), never the main path. Delivery is at-least-once, so make side effects idempotent where the provider allows.
- Clients never poll for data. They read once, then re-read when the server signals a change over the app's one live HTTP stream (`notifications.subscribe`): after the write commits, publish a content-free signal on a narrow topic (a user, Space or bot) through the realtime fanout, and the client re-reads through its normal authorized RPC. The stream signals on every (re)connect, so reconnecting is the catch-up, along with re-reading on window focus or app foreground. Add no timed backup re-reads and no polling fallback while the stream is down; instead make a missed signal rare: retry the publish through brief database outages, and end the stream when a subscription fails so the client reconnects. Timers are only for what is not a data read: clocks, presence heartbeats, and short waits on a third party (an OAuth redirect) while someone watches.
- Dependency security audits include build/release dependencies and assert workspace package coverage; scanning only the package-manager YAML document is not a passing audit.
- Treat auth, secret handling, sandbox boundaries, host commands, and integrations as security-sensitive. A new column holding a sealed value (its name contains `cipher`) goes in `packages/adapters/src/secrets/secret-holder-columns.json`: under `checked` if it can hold a remote store entry (the write-ahead cleanup looks up every column listed there before deleting one), or under `neverRemote` if it never does. Keep tests deterministic and offline by default.
- Judge natural-language meaning and factual claims with an LLM and an explicit, versioned rubric calibrated against reviewed examples; do not grade free-form prose with keyword lists, regexes, or exact wording (the `no-keyword-graded-evals` check holds eval code to this). Keep deterministic assertions for observable effects and structured output contracts. Keep judge calls opt-in and provider-neutral, report their cost separately, and treat judge errors as unqualified results rather than passes.
- The desktop Playwright suite (`pnpm --filter @rakazo/desktop test:e2e`) opens real Electron windows and steals focus on macOS. Do not run it on a maintainer's machine as routine verification; run the tests that cover your change locally (not the whole suite) and let CI's virtual-display job run the e2e on push. The web e2e suite (`pnpm test:e2e`) is also left to CI as routine verification: update the specs, push, and read the CI run.
- Marketing pages (the Astro site in `apps/www`) don't need new tests or CI screenshots beyond the existing homepage screenshot suite, and may name third-party vendors and providers; the product's rules on vendor names and UI tests don't apply there. Check those changes visually and with a build. Only the home page, docs and the shared layout live in this repository; every other page (comparisons, blog, pricing, legal) lives in the private `rakazobot/marketing` repository, which Vercel clones into the ignored `apps/www/src/marketing/`, so make those changes there.
- Do not edit `CHANGELOG.md` in feature pull requests; the release skill (`.agents/skills/release/SKILL.md`) writes it from merged pull requests when a version is cut, so write the PR's `## What` and `## Risk` for that reader.
- After creating a pull request, stay with it until CI and automated review bots have finished; passing checks alone do not mean the review is complete. Follow `.agents/skills/pr-watch/SKILL.md`: run its `pr-digest --watch` helper as a single backgrounded call that blocks until a new review comment or check failure arrives or the checks on the current head commit are terminal, then act on the verdict it prints and watch again. Do not poll in the foreground on a timer, which mostly buys repeated snapshots of an unchanged PR and dies at the tool timeout. Address every actionable issue, push the fixes, and repeat until no actionable feedback remains. Do not merge while review bots are still pending or review issues remain unresolved.
- Ignore the Vercel "Authorization required to deploy" failure on fork PRs; it is expected and not required.
- PR descriptions start with `## What`: a short plain-language paragraph explaining what the PR does, simple enough for someone who has never seen the code. Then `## Why`: the product reason in the same plain words, what was wrong or missing and who it hurt. Then `## Changes`: behavior and decisions a reviewer needs, not a tour of files, libraries, or internals the diff already shows; at most about 8 bullets. Add `## Risk` only when there is one (security, migrations, limits, irreversible effects). End with `## Tested`: a short paragraph naming the kinds of tests run and what was not tested, not a list of every case. Keep it under about 350 words unless the change is security- or migration-heavy. Write as the author, never as a third-person briefing about the maintainer.
- Commit messages, PR descriptions, issues, and review replies are public too. Describe test results in words instead of pasting tool output. Never include business metrics such as analytics, traffic, click-through, conversion, signup, revenue, or star-growth numbers; give the product reason in words, even when data motivated the change. Never include anything that identifies a person, machine, or account: local paths, usernames, hostnames, signing identities, legal entity names, Apple Team IDs, API key IDs, issuer or tenant IDs, account emails, or the accounts, machines, and files that secret values came from. Naming the secrets a workflow reads is fine; use placeholders when a value must be shown.
- For UI changes, embed the CI E2E screenshot that shows the change in the PR description (`pr-watch` covers how, once CI publishes it); add the web test that opens that screen if it is missing. For native-only mobile UI that CI cannot capture, never link an unrelated web screenshot; for a large native change, add a flow to the existing iOS screenshot catalog. Whenever you captured screens while verifying a change (simulator, emulator, or browser), attach the ones that show it (`pr-watch` covers how) unless they show private data; say so only when you have none. Never add feature-specific flags, runners, or fake services to shared test or screenshot tooling to capture one screen; if the existing fixtures cannot show it, say so instead.
- Review bots ask how to make the code work as written, never whether it should exist. Before fixing a finding, decide whether the flagged code belongs in the PR; remove speculative, unrun, or out-of-scope code instead of building more to support it, and refute wrong findings with evidence.
- Translation source exclusions use `<rootDir>`-anchored globs so builds invoked from app folders exclude test helpers, dependencies and generated catalogs; `scripts/checks/i18n-source-paths.test.mjs` verifies actual discovery from the root and web app.
- Feature PRs add or change UI strings in code only: never run `intl:extract` or edit translation catalogs (`messages.po`) in them. Builds show untranslated strings in English, and a workflow on main keeps one "Update translation catalogs" PR in step; translations go there or in their own translation-only PR. The one exception is adding a UI language, which commits its new catalog.
- Keep each PR to one feature or fix. A large PR is fine; bundling unrelated features is not, so open a separate PR for each.
- When reviewing a PR, judge it against this file. Recommend removing code that cannot work or does not belong rather than suggesting more code to support it, and flag changes the PR description does not mention, such as new vendor or provider presets, dependencies, test runners, environment variables, or edits to shared tooling.
- UI system. Colors live in `@rakazo/ui-tokens` as semantic tokens (background, card, muted, border, primary, destructive, ...) with one TypeScript source that generates `tokens.css`; never hardcode a product hex or use `[var(--…)]` arbitrary values. Web and Electron use shadcn/ui on Base UI, vendored into `packages/ui-web` via `pnpm exec shadcn add` from the official registry only (third-party registries are a supply-chain risk); reuse those components before writing chrome by hand (section headings use `SectionHeading`; a dropdown over a fixed list uses `OptionSelect`, never the browser's own select), and reuse `apps/web/src/components/ai/` for AI moments (loading, shimmer, success). A Button, select, Input and InputGroup take their height from the `size` prop, never a height class (`h-*`, `min-h-*`, `size-*`) in `className`: each size name is one height on every control (`packages/ui-web/src/lib/control-size.ts`), so controls side by side line up (the `no-control-height-classes` check holds this). The app is monochrome: primary is ink, status colors are destructive/success/warning, bots carry the only identity color. Mobile is native-first: Expo Router, Expo UI, native sheets, menus, alerts and pickers wherever one exists; custom surfaces (thread, composer, avatars, cards) use plain StyleSheet with the shared tokens through `apps/mobile/lib/appearance/appearance.ts`, and system chrome stays PlatformColor via `lib/native/native.ts`. Mobile may diverge from web when the native pattern is better.
- On mobile, use built-in native iOS controls (@expo/ui SwiftUI and Liquid Glass, native header items, context menus, alerts, pickers, and switches) wherever possible instead of custom React Native pills or buttons.
